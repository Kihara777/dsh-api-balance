# Security Policy

[中文](../SECURITY.md) | English | [日本語](SECURITY.ja.md) | [偽中国語](SECURITY.pcn.md)

## Supported Versions

This plugin runs inside a DeepSeek Harness (DSH) host, and **only the latest `main` branch**
receives security fixes. Historical commits are not maintained separately -- if you need an
older version, please fork it and carry the maintenance yourself.

## Reporting a Vulnerability

Please **do not** report security issues through public issues. Use GitHub's
[private vulnerability reporting](https://github.com/Kihara777/dsh-api-balance/security/advisories/new)
channel, or email the maintainer.

Please include where possible: the affected version / commit, reproduction steps, expected
versus actual behaviour, and the threat model you have in mind (who can trigger it, and what
preconditions are required).

## Response Time

The maintainer (Kori) has a Class-1 visual disability and works day to day with a
vision-assistance agent. We aim to give a first reply within **7 days**; a full assessment of a
complex issue may take longer -- but **every report gets an answer**.

## Known Design Boundaries

The following are **not** vulnerabilities but deliberate behaviour; please confirm before reporting:

| Item | Explanation |
|---|---|
| Reading the platform token from browser Local Storage | The "platform token" is acquired by **scanning the local browser session automatically**, **on by default and disableable in settings**; only the token is read, no other browser data is collected, and the token is written to disk with `0600` |
| The 6-hour throttle on token scanning | `config.browserScanIntervalMs` defaults to 6 hours; within the window no rescan happens, but the previous scan report is returned |
| Balance / usage queries reach an external API | `/user/balance` and usage statistics request DeepSeek's official endpoints with the plugin's configured token -- this is the plugin's **core function**, not data exfiltration |
| Endpoints ride DSH's `/api` channel | This plugin's HTTP endpoints get their authentication and Host-authority (`trustedHosts`) boundary from the **DSH host**; the plugin does not build its own auth layer |

### On the missing-rate-limit reports

Repeated scanner reports claim several endpoints lack rate limiting. **After checking each one we
judged them false positives**, for these reasons:

**1. The description does not match the diff.** The PR claims to affect `/token`,
`/token/clear`, `/voicepack` and `/tts`, but its **diff only changes `/query`** -- one path.

**2. Its rate-limit key does not hold in this deployment.** The PR keys on
`x-forwarded-for`, a header the **client supplies and can forge freely**; more importantly,
calls to this plugin come from a **same-origin page over DSH's `/api` RPC channel, which does
not carry `x-forwarded-for`** -- so every local request lands in the same `"unknown"` bucket and
**a normal user would hit their own limit first**.

**3. The key endpoints already have throttles.** `/token` already has a **6-hour** server-side
throttle (`browserScanIntervalMs`), and voice announcements are limited to **30 minutes**.

**4. This plugin has no high-frequency polling.** The only 30-second `setInterval` in the source
runs `isPeakPricing()` (**a purely local time check** for peak/off-peak pricing hints) and
**issues no network request**; another poll runs on a 15-minute interval. Estimated at human
operating speed, the most active usage is roughly **5-10 calls per minute** -- the scanner's
suggested 30/minute is already 3-6 times that, effectively unreachable by a human.

**5. The real boundary is not at the application layer.** Endpoint reachability is decided by the
**DSH host's authentication plus Host authority**. Anyone who could cross that boundary would not
be stopped by a 30-per-minute limit, while the limit would harm ordinary refreshing (clicking
repeatedly while waiting for a balance refresh is normal behaviour).

**Conclusion and trade-off**: **no code change** for this. Should a layer of defence genuinely be
wanted later, the right approach is to rate-limit **by authenticated principal rather than by
IP** (IPs can be forged), with a threshold **far above any human interaction** (say 60-120 per
minute), positioned as "runaway-script protection" rather than "attack protection" -- and the
host-side boundary should be hardened first, instead of adding an application-layer limit that
stops nobody and may harm real users.

> **We welcome evidence-backed corrections to any conclusion above.** Our process is "review
> first, reply second, attach evidence" rather than accepting reports at face value.

### On duplicate submissions

**The same conclusion already listed above, resubmitted without new evidence, will be closed
directly with a pointer to this section.**

| Accepted | Closed directly |
|---------|-------------|
| A **new** issue not covered above | A repeat of the same conclusion above with no new evidence |
| Showing that a conclusion above is **wrong**, with reproducible evidence | Merely restating an existing conclusion |
| The same topic but a **different** threat model or exploitation path | Another automated scan output for the same rule |

## Supply Chain Notes

- This repository **contains no secrets**; the platform token is obtained at runtime from
  configuration or the local browser session and written to the user's directory with `0600`
- No npm package is published (the maintainer is visually impaired and cannot currently complete
  the npm submission process on her own); install from GitHub sources, or declaratively via the
  [NixKits](https://github.com/Kihara777/NixKits) thin wrapper
